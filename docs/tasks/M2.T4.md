# M2.T4: Accept wallet payments and expose authenticated history

Status: planned; no implementation in this change.

**Outcome:** A signed payment is durably accepted once, owned by the right account and recoverable
before any transfer exists.

**Learn:** Authenticated handlers, idempotent acceptance and server-backed history.

- Depends on: [M1.T4](M1.T4.md), [M2.T1](M2.T1.md), [M2.T2](M2.T2.md).
- Primary journey ownership: J8.S4.
- Policy: D26, D44, D111, D140, D231. Invariants: I5, I12.
- Rough effort: 2–3 focused developer days, excluding external waits.
- Expected locations: packages/server/src/payments, handlers and read models.

Read the linked [decisions](../decisions.md), exact criteria in the
[journey spine](../journeys/settle-kit.yaml), and [technical
design](../plans/2026-10-15-deposit-sdk-technical-design.md).
Use the [checkpoint protocol](README.md#how-we-implement-together). Implement one
checkpoint per turn unless Vinay explicitly asks for a longer run.

## Checkpoint 1: Accept only the stored consent

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Implement submitPayment against the saved quote, owner and signature. Check current
route, expiry, gas reserve and limits. Atomically store acceptance and its operation before
scheduling; repeats return the original result.

**Check:** Race duplicate submissions, change the authorization and lose the response
(J8.S4.c2–c5/c7–c8). Crash between commit and scheduling; due-work recovery must find the same
operation.

**Walk through:** What does an acceptance response promise, and what money movement has it proved?

## Checkpoint 2: Wire the first wallet payment end to end

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Connect real address issuance and the accepted workflow's ensure_contract stage. A fresh
account must not need a manual deposit first. Keep signed validity unchanged while
deployment/submission proceeds.

**Check:** Use real Postgres and the local contract runner for an undeployed recipient, concurrent
deployment and restart after broadcast (J8.S5.c18, I12). Verify deployment success alone never
appears as payment success.

**Walk through:** Which record gives preparation the recipient before there is any code at that
address?

## Checkpoint 3: Expose recoverable account history and simulation

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Implement authenticated getPayment/listDeposits with distinct item kinds and one identity
as a transfer arrives. Omit unsigned drafts. Supply deterministic simulated manual and wallet
scenarios through the same stored transitions.

**Check:** Use two accounts and reload with no cached payment ID (J8.S4.c6/c9, J8.S8.c5,
J9.S1.c2–c3). Start simulated paths without live dependencies (J1.S2.c12–c13).

**Walk through:** How does Alice recover an accepted attempt after losing all browser state?

**Out of scope:** Cancellation endpoint, arbitrary-recipient payments and browser-held operator
keys.

## Done and handoff

Acceptance, ownership and pre-transfer history work with the runtime. The preview can now use
simulation; real combined-route proof remains M2.T5.

**Keep as evidence:** One lost-response sequence from submitPayment to authenticated history and the
recovered original operation.

Use exact criterion/invariant IDs in tests; see the shared protocol for naming,
merge checks and the checkpoint handoff. Do not start the next task automatically.
