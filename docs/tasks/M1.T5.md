# M1.T5: Build the immutable Solana vault and payment program

Status: planned; no implementation in this change.

**Outcome:** The source program can accept only the supported USDC route and cannot redirect funds
or replay payments.

**Learn:** Solana accounts, program-derived addresses (PDAs), associated token accounts (ATAs),
Rust/Anchor, cross-program invocation (CPI) validation and persistent replay guards.

- Depends on: [M1.T1](M1.T1.md).
- Primary journey ownership: J1.S4a, J15.S2.
- Policy: D136, D137, D232–D234; D26, D28, D126, D128. Invariants: I1, I5, I11, I12.
- Rough effort: 4–6 focused developer days, excluding external waits.
- Expected locations: Owned Solana program/IDL and versioned cluster manifest; no packages installed during planning.

Read the [decisions](../decisions.md), exact [journey criteria](../journeys/settle-kit.yaml),
and the Solana section of the [technical design](../plans/2026-10-15-deposit-sdk-technical-design.md).
Follow the [checkpoint protocol](README.md#how-we-implement-together): one checkpoint per turn,
actual-file walkthrough, focused checks and a pause for Vinay. Split a checkpoint before editing
if it cannot be reviewed in one sitting. All boxes remain unchecked.

## Checkpoint 1: Derive and initialize one immutable vault

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Define one versioned byte commitment for namespace, account and every D136 setting.
Implement initialization, canonical PDA/ATA derivation and runtime manifest/immutability checks. Pin
token/CCTP accounts; validate owners, mint, authority, discriminators and unexpected delegate/close
authority.

**Check:** Use the Rust/Anchor local validator and Bun codec vectors for J1.S4a.c1–c4 and I11.
Front-run initialization with changed settings, supply a counterfeit mint/program and attempt to
replace a stored recipient.

**Walk through:** Why can a PDA control USDC without any deposit private key?

## Checkpoint 2: Execute isolated exact payments and full manual drains

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Implement separate manual and payment vault paths. Full drains require the expected
sequence and advance it; wallet payments require payer and stored host co-signer signatures, exact
commitment and persistent receipt. Construct tags and complete Circle/Settle Kit frames inside the
program; apply all checks before CPI.

**Check:** Prove I11/I12 and J13.S4.c2–c4/J14.S4.c2–c4 with repeated payment IDs, stale sequences,
changed CPI accounts, equal-amount burns, fee-bound edges and a failing CPI. Use checked u64
arithmetic; no payer USDC debit/fee may survive a failed atomic call.

**Walk through:** Which account stops a refreshed transaction from charging the same quoted payment
again?

## Checkpoint 3: Implement guarded recovery and freeze the release artifact

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Implement J15.S2.c1–c5 for over-limit USDC, legacy-SPL assets and surplus SOL. Preserve
required rent, reusable vault state and permanent payment receipts. Build reproducible artifacts and
an operator deployment procedure that verifies removed upgrade authority.

**Check:** Generate repeated/cross-ordered drain, recovery and payment calls for I1/I11/I12. Check
no-limit recovery rejection, USDC rescue rejection, Token-2022 rejection and failed transfer without
success evidence. Label local-validator proof separately from deployed CCTP compatibility.

**Walk through:** Why must recovering funds never delete the sequence or used-payment receipt?

**Out of scope:** Database/workflows, production deployments, wallet prompts and claims that local
CPI fixtures prove the live route.
