## Goal

The database is where every duplicate is stopped. This task builds the tables, the
constraints, and a small internal store whose every write is either a unique insert or
a compare-and-set (CAS) transition that also appends a timeline entry in the same
transaction. Workflows (T5) call only this store.

## Tables

As in design §4, plus two additions marked ★:

```text
settle_kit_deposit_addresses
  id, account_id, route jsonb, router, network ('mainnet' | 'test'), address,
  last_reconciled_at, ★ last_activity_at, created_at
  UNIQUE (router, network, address)
  UNIQUE (account_id, router, network, route)

settle_kit_deposits
  id, address_id (nullable), ★ order_id (nullable), router, network, fill_id, deposit_tx, status, amount_in numeric,
  amount_out numeric, dest_chain_id, dest_tx, dest_log_index, refund_evidence jsonb,
  run_id, delivery_run_id, settlement_event jsonb, delivery_attempts int default 0,
  delivery_next_attempt_at, delivery_error, error_code, created_at, updated_at
  UNIQUE (router, network, fill_id)
  UNIQUE INDEX NULLS NOT DISTINCT (dest_chain_id, dest_tx, dest_log_index)
    WHERE dest_chain_id IS NOT NULL AND dest_tx IS NOT NULL

settle_kit_deposit_events
  deposit_id, seq, status, at, actor, evidence jsonb
  PRIMARY KEY (deposit_id, seq)

settle_kit_send_attempts
  id, address_id, attempt_key, tx_hash, created_at
  UNIQUE (attempt_key)

★ settle_kit_orders                      (design §6a)
  id, account_id, external_id, amount_out numeric, price jsonb, route jsonb,
  address, amount_in numeric, status, expires_at, created_at, updated_at
  UNIQUE (account_id, external_id)
  UNIQUE (address)
```

A deposit row has exactly one of `address_id` (deposit mode) or `order_id` (checkout);
enforce it with a `CHECK`.

★ `last_activity_at` is set when an address is created or reused and when a fill is
inserted; reconciliation tiers use it (design §6). ★ The transition table from T2 is
enforced in code, not by a database trigger.

If Drizzle's builder can't express the partial `NULLS NOT DISTINCT` index, write it as
raw SQL in the migration and leave a comment in `schema.ts` pointing to it.

Normalisation: EVM addresses lowercase. `route` is canonical JSON (fixed key order:
`from.chainId, from.token, to.chainId, to.token, treasury, refundTo, recoveryAddress`),
so the same route always produces the same `jsonb` value.

## `DepositStore`

```ts
export type DepositStore = {
  getOrCreateAddress(input: {
    accountId: string; router: string; network: "mainnet" | "test";
    route: CanonicalRoute; create: () => Promise<Address>;
  }): Promise<AddressRow>;
  findAddress(q: { router: string; network: string; address: Address }): Promise<AddressRow | null>;

  insertFillIfNew(input: { addressId: string; fillId: string; depositTx: Hex | null }):
    Promise<{ inserted: boolean; deposit: DepositRow }>;

  transition(input: {
    id: string; from: DepositStatus[]; to: DepositStatus;
    patch?: { errorCode?: string; refundEvidence?: RefundEvidence; runId?: string };
    actor: "system" | "operator"; evidence: Record<string, unknown>;
  }): Promise<DepositRow | null>;               // null = CAS lost or move not allowed

  settle(input: {
    id: string; from: DepositStatus[];
    amountOut: bigint; destination: { chainId: number; txHash: Hex; logIndex: number };
    event: SettledEvent; now: Date;
  }): Promise<"settled" | "transfer_claimed" | "stale">;

  markCredited(id: string): Promise<boolean>;
  recordDeliveryFailure(input: { id: string; error: string; nextAttemptAt: Date | null }): Promise<void>;

  getDeposit(id: string): Promise<{ deposit: DepositRow; timeline: TimelineEntry[] } | null>;
  listDeposits(q: { accountId?: string; addressId?: string; status?: DepositStatus; limit: number }): Promise<DepositRow[]>;
  listUnfinished(q: { now: Date; limit: number }): Promise<DepositRow[]>;
  listAddressesDue(q: { now: Date; limit: number }): Promise<AddressRow[]>;
  markAddressScanned(id: string, at: Date): Promise<void>;

  recordSendAttempt(input: { addressId: string; attemptKey: string }): Promise<{ inserted: boolean }>;

  createOrder(input: {
    accountId: string; externalId: string; amountOut: bigint; price: unknown; expiresAt: Date;
    route: CanonicalRoute; create: () => Promise<{ address: Address; amountIn: bigint }>;
  }): Promise<OrderRow>;
  getOrder(id: string): Promise<OrderRow | null>;
  findOrderByAddress(address: Address): Promise<OrderRow | null>;
  insertOrderFillIfNew(input: { orderId: string; fillId: string; depositTx: Hex | null }):
    Promise<{ inserted: boolean; deposit: DepositRow }>;
  setOrderStatus(id: string, status: OrderStatus): Promise<void>;
  listOrdersDue(q: { now: Date; graceMs: number; limit: number }): Promise<OrderRow[]>;
};
```

### Rules

1. **`getOrCreateAddress`** returns the existing row if one matches
   `(account, router, network, route)`; `create` is not called. Otherwise it calls
   `create()` (a Relay quote), then inserts. If a concurrent call won the insert, return
   the winner's row; the extra Relay address is simply never used.
2. **`insertFillIfNew`** inserts with status `waiting` and timeline `seq 1`; on the
   `(router, network, fill_id)` conflict it returns the existing row with
   `inserted: false`. Router and network are copied from the address.
3. **`transition`** checks `canTransition` (T2) for each `from`, then runs one
   transaction: `UPDATE … SET status = to … WHERE id = $1 AND status = ANY($from)`, and
   only if a row changed, appends the next timeline entry
   (`seq = max(seq) + 1` for that deposit). Returns `null` if nothing changed.
4. **`settle`** is one transaction: CAS to `settled`, write amount, destination fields,
   `settlement_event`, `delivery_next_attempt_at = now`, and the timeline entry.
   A unique violation on the transfer index returns `"transfer_claimed"` and changes
   nothing (the workflow then moves the deposit to `needs_attention`). A lost CAS
   returns `"stale"`.
5. **`markCredited`** CAS `settled → credited`, clears `delivery_next_attempt_at`,
   appends the timeline entry. Returns `false` if already credited.
6. **`recordDeliveryFailure`** increments `delivery_attempts`, sets `delivery_error`
   and `delivery_next_attempt_at` (null when exhausted), appends a `delivery_failed`
   entry. Status stays `settled`.
7. **`listUnfinished`** returns deposits that are not final (excluding `settled`), plus
   `settled` deposits whose `delivery_next_attempt_at <= now`. Oldest `updated_at` first.
8. **`listAddressesDue`**: never-scanned addresses first; then addresses whose
   `last_activity_at` is within 30 days and `last_reconciled_at` is over 15 minutes old;
   then older ones not scanned for a day. Bounded by `limit`.
9. Amounts are written from `bigint` and read back as `bigint`; never via `Number`.
10. **`createOrder`** returns the existing order for the same `(accountId, externalId)`
    without calling `create` (the host may retry). Otherwise it calls `create()` (a strict
    Relay quote) and inserts with status `pending`.
11. **`listOrdersDue`** returns `pending` orders not yet past `expires_at + graceMs`, for
    reconciliation to scan their addresses.

## Acceptance tests

1. The migration applies cleanly to an empty schema.
2. `getOrCreateAddress` twice for the same account and route calls `create` once and
   returns the same row; a different route creates a second row.
3. Two concurrent `getOrCreateAddress` calls (`Promise.all`) for a new route return the
   same row.
4. Route JSON with different key order or address casing maps to the same row.
5. `insertFillIfNew` twice with the same fill id: first `inserted: true`, second
   `false`, one row, one timeline entry.
6. `transition` follows the table: `waiting → processing` succeeds; a second identical
   call returns `null`; `credited → processing` returns `null` without touching the row.
7. Ten concurrent `transition(waiting → processing)` calls on one deposit: exactly one
   succeeds, and the timeline has exactly one new entry.
8. `settle` on two different deposits claiming the same `(chain, tx, logIndex)`: the
   first returns `settled`, the second `transfer_claimed` and stays unchanged.
9. Two unfinished deposits with null destination fields coexist (the partial index
   doesn't block them).
10. `settle` then `markCredited`: status `credited`, `delivery_next_attempt_at` null,
    timeline `waiting → … → settled → credited` with increasing `seq`.
11. `recordDeliveryFailure` keeps the status `settled` and appears in `listUnfinished`
    once due; with `nextAttemptAt: null` it no longer appears.
12. `amount_out` of `10n ** 30n` round-trips exactly.
13. `listAddressesDue` returns a never-scanned address before a recently active one,
    and skips an address scanned 5 minutes ago.
14. `recordSendAttempt` with the same key twice: `inserted` true then false.
15. `createOrder` twice with the same `externalId`: `create` called once, one row.
16. A deposit row with both or neither of `address_id` and `order_id` is rejected.
17. `listOrdersDue` includes a pending order within the grace period and excludes a
    paid one and one past expiry + grace.
