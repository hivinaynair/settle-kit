# T3 · Postgres schema + Drizzle store (orders, payments, timeline)

**Read first:** design doc §0 (build scope), §4 (Storage and state, Concurrency), §6a
(Orders), §10.2 (timeline). **Depends on:** T1, T2.
**Time box:** ~3 hours. **Branch:** `vinay/t3-store`.
**Done when:** the acceptance tests pass against a real Postgres 15+ database and
lint/types are clean.

---

## Goal

The database is where duplicates are stopped. This task builds three tables and a small
store whose every write is either a unique insert or a compare-and-set (CAS) update
("only change it if it's still in the state I expect"), and every state change appends
a timeline entry in the same transaction. The workflow (T5) calls only this store.

Checkout only. Deposit addresses (top-ups), send attempts and reconciliation queries
arrive with their features later.

## Tables

```text
settle_kit_orders
  id, account_id, external_id,
  amount numeric,          -- exact USDC base units the merchant must receive
  pay_amount numeric,      -- what the payer must send (from the quote)
  route jsonb,             -- canonical route incl. recipient and refundTo, addresses lowercased
  display jsonb,           -- { title, image } for the checkout screen only
  address text,            -- the order's single-use deposit address (null until a route is picked)
  router_request_id text,  -- Relay's original request ID for that quote; set with address, same CAS
  test boolean not null,   -- created in test mode; a live deployment never processes it
  simulation jsonb,        -- test mode only: { scenario, startedAt } for the simulated router (T5)
  expires_at, created_at, updated_at
  UNIQUE (account_id, external_id, test)   -- same order twice returns it; test and live never collide
  UNIQUE (address)
  UNIQUE (router_request_id, test)         -- one router request belongs to one order per mode

settle_kit_deposits        -- one row per payment Relay reported for an order (root or child request)
  id, order_id → orders, fill_id, status,  -- fill_id: that report's own request ID, never the root's
  deposit_tx, received_amount numeric,   -- verified on chain; equals the order amount
  dest_chain_id, dest_tx, dest_log_index,
  settlement_event jsonb,  -- the immutable webhook payload
  delivery_attempts int default 0, delivery_error,
  created_at, updated_at
  UNIQUE (order_id, fill_id)                                   -- a payment is recorded once
  UNIQUE INDEX NULLS NOT DISTINCT (dest_chain_id, dest_tx, dest_log_index)
    WHERE dest_tx IS NOT NULL                                  -- a transfer settles one payment
  UNIQUE INDEX (order_id) WHERE status IN ('settled', 'credited')  -- an order is paid once

settle_kit_deposit_events  -- the timeline
  deposit_id → deposits, seq, status, at, actor, evidence jsonb
  PRIMARY KEY (deposit_id, seq)
```

The order's status isn't stored: it's derived with `orderStatusFor` (T2) from its
payment and `expires_at`. One less thing to keep in sync.

## `Store`

```ts
export type Store = {
  createOrder(input: {
    accountId: string; externalId: string; amount: bigint; expiresAt: Date; test: boolean;
    display?: { title: string; image?: string };
  }): Promise<OrderRow>;
  /** Simulated router (T5) looks up the order behind a request ID, in one mode only. */
  findOrderByRequestId(requestId: string, test: boolean): Promise<OrderRow | null>;
  /** Test mode only: start a simulated scenario once (CAS on simulation IS NULL). */
  simulate(input: { orderId: string; scenario: string; startedAt: Date }): Promise<boolean>;
  /** Buyer picked a route: store address, payAmount and requestId once, together. */
  setOrderRoute(input: { orderId: string; route: Route;
                         create: () => Promise<OrderAddress> }): Promise<OrderRow>;
  /** payment: the order's main payment (rule 8); timeline: that payment's entries. */
  getOrder(id: string): Promise<{ order: OrderRow; payment: PaymentRow | null;
                                  timeline: TimelineEntry[] } | null>;

  recordPayment(input: { orderId: string; fill: Fill }): Promise<{ inserted: boolean; payment: PaymentRow }>;
  transition(input: { id: string; from: DepositStatus[]; to: DepositStatus;
                      evidence: Record<string, unknown> }): Promise<PaymentRow | null>;
  settle(input: { id: string; receivedAmount: bigint;
                  destination: { chainId: number; txHash: Hex; logIndex: number };
                  event: SettledEvent }): Promise<"settled" | "transfer_claimed" | "order_paid" | "stale">;
  markCredited(id: string): Promise<boolean>;
  recordDeliveryFailure(input: { id: string; error: string }): Promise<void>;
};
```

### Rules

1. **`createOrder`** returns the existing order for the same `(accountId, externalId, test)`
   (the app may retry). No Relay call yet: the address depends on the route the buyer
   picks.
1b. **`setOrderRoute`** calls `create()` (a strict Relay quote) only if the order has no
   address yet, and stores `route`, `address`, `pay_amount` and `router_request_id` in
   one CAS on `address IS NULL`. A second call (or a retry after a lost race) returns the
   stored row: never an address from one quote with the request ID of another, and never
   overwriting a chosen quote. `OrderRow` gains `routerRequestId: string | null`; a
   routed order has both or neither.
1c. **Request ID vs payment ID.** `router_request_id` is how T5 asks Relay about the
   order. Each payment row keeps its report's own `fill_id` (a child request has its own
   ID); the root ID replaces none of the per-fill, per-transfer or paid-once
   constraints. The address stays stored for the buyer's instructions and support.
2. **`recordPayment`** inserts with status `waiting` and timeline `seq 1`; the same
   `(orderId, fill.id)` again returns the existing row with `inserted: false`.
3. **`transition`** checks `canTransition` (T2), then in one transaction:
   `UPDATE … SET status = to WHERE id = $1 AND status = ANY($from)`, and only if a row
   changed, appends the next timeline entry. Returns `null` if nothing changed.
4. **`settle`** is one transaction: CAS to `settled`, write amounts, destination and
   `settlement_event`, append the timeline entry. A unique violation on the transfer index
   returns `"transfer_claimed"`, one on the paid-once index returns `"order_paid"` (a
   second payment to the same order; T5 sends it to `needs_attention`), and both change
   nothing; a lost CAS returns `"stale"`.
5. **`markCredited`** CAS `settled → credited` plus a timeline entry; `false` if already
   credited.
6. **`recordDeliveryFailure`** increments `delivery_attempts`, stores the error, appends
   a `delivery_failed` entry; the status stays `settled`.
7. Amounts go in and come out as `bigint`; never through `Number`.
8. **The order's main payment.** Strict addresses mean Relay fills an order at most once,
   but a second deposit still arrives as its own report (usually refunded), so an order
   can have more than one payment row. `getOrder` returns the `settled`/`credited` one if
   it exists (the paid-once index allows at most one), otherwise the most recently
   created. Its status feeds `orderStatusFor`. Other rows stay in the database and
   their own timelines for the merchant to follow up.

## Acceptance tests

1. The migration applies cleanly to an empty schema.
2. `createOrder` twice with the same `externalId`: one row. `setOrderRoute` twice:
   `create` called once, same address and request ID; the row never shows an address
   without its request ID.
3. `recordPayment` twice with the same fill: one row, one timeline entry.
4. `transition` follows the table; a repeated or disallowed move returns `null` and
   changes nothing.
5. Ten concurrent `transition(waiting → processing)` calls: exactly one succeeds, one new
   timeline entry.
6. Two payments claiming the same on-chain transfer: the first `settle` returns
   `"settled"`, the second `"transfer_claimed"`.
7. `settle` then `markCredited`: timeline reads `waiting → … → settled → credited` with
   increasing `seq`; `getOrder` derives order status `paid`.
8. `recordDeliveryFailure` keeps `settled` and adds a `delivery_failed` entry.
9. An amount of `10n ** 30n` round-trips exactly.
10. Two payments of one order, different transfers: the first `settle` returns
    `"settled"`, the second `"order_paid"`.
11. `simulate` twice: the first returns `true`, the second `false`;
    `findOrderByRequestId` finds the order in its own mode and returns `null` for the
    other mode.
12. Two concurrent `setOrderRoute` calls whose `create` returns different quotes: one
    pair is stored whole; both calls return that same address and request ID.
13. The same request ID on two orders in one mode → unique violation; in test and live →
    allowed.
14. A root fill and a child fill (different `fill.id`) for one order → two payment rows.
15. Root `credited`, then a child recorded and moved to `needs_attention`: `getOrder`
    returns the root as the payment and the order reads `paid`. With no paid row, the
    newest payment is returned.
