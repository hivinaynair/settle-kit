# T3 · Postgres schema + Drizzle store (orders, payments, timeline)

**Read first:** design doc §0 (build scope), §4 (Storage and state, Concurrency), §6a
(Orders), §10.2 (timeline). **Depends on:** T1, T2.
**Time box:** ~3 hours. **Branch:** `vinay/t3-store`.
**Done when:** the acceptance tests pass against a real Postgres 15+ database and
lint/types are clean.

---

## Goal

The database is where duplicates are stopped. This task builds three tables and a small
store whose every write is either a unique insert or a compare-and-set (CAS) update
("only change it if it's still in the state I expect"), and every state change appends
a timeline entry in the same transaction. The workflow (T5) calls only this store.

Checkout only. Deposit addresses (top-ups), send attempts and reconciliation queries
arrive with their features later.

## Tables

```text
settle_kit_orders
  id, account_id, external_id,
  amount numeric,          -- exact USDC base units the merchant must receive
  pay_amount numeric,      -- what the payer must send (from the quote)
  route jsonb,             -- canonical route incl. recipient and refundTo, addresses lowercased
  address text,            -- the order's single-use deposit address
  expires_at, created_at, updated_at
  UNIQUE (account_id, external_id)   -- creating the same order twice returns it
  UNIQUE (address)

settle_kit_deposits        -- one row per payment Relay saw at an order's address
  id, order_id → orders, fill_id, status,
  deposit_tx, paid_amount numeric, received_amount numeric,
  dest_chain_id, dest_tx, dest_log_index,
  settlement_event jsonb,  -- the immutable onSettled payload
  delivery_attempts int default 0, delivery_error,
  created_at, updated_at
  UNIQUE (order_id, fill_id)                                   -- a payment is recorded once
  UNIQUE INDEX NULLS NOT DISTINCT (dest_chain_id, dest_tx, dest_log_index)
    WHERE dest_tx IS NOT NULL                                  -- a transfer settles one payment

settle_kit_deposit_events  -- the timeline
  deposit_id → deposits, seq, status, at, actor, evidence jsonb
  PRIMARY KEY (deposit_id, seq)
```

The order's status isn't stored: it's derived with `orderStatusFor` (T2) from its
payment and `expires_at`. One less thing to keep in sync.

## `Store`

```ts
export type Store = {
  createOrder(input: {
    accountId: string; externalId: string; amount: bigint; route: Route; expiresAt: Date;
    create: () => Promise<OrderAddress>;  // calls router.orderAddress()
  }): Promise<OrderRow>;
  getOrder(id: string): Promise<{ order: OrderRow; payment: PaymentRow | null;
                                  timeline: TimelineEntry[] } | null>;

  recordPayment(input: { orderId: string; fill: Fill }): Promise<{ inserted: boolean; payment: PaymentRow }>;
  transition(input: { id: string; from: DepositStatus[]; to: DepositStatus;
                      evidence: Record<string, unknown> }): Promise<PaymentRow | null>;
  settle(input: { id: string; receivedAmount: bigint;
                  destination: { chainId: number; txHash: Hex; logIndex: number };
                  event: SettledEvent }): Promise<"settled" | "transfer_claimed" | "stale">;
  markCredited(id: string): Promise<boolean>;
  recordDeliveryFailure(input: { id: string; error: string }): Promise<void>;
};
```

### Rules

1. **`createOrder`** returns the existing order for the same `(accountId, externalId)`
   without calling `create` (the app may retry). Otherwise it calls `create()` (a Relay
   quote) and inserts.
2. **`recordPayment`** inserts with status `waiting` and timeline `seq 1`; the same
   `(orderId, fill.id)` again returns the existing row with `inserted: false`.
3. **`transition`** checks `canTransition` (T2), then in one transaction:
   `UPDATE … SET status = to WHERE id = $1 AND status = ANY($from)`, and only if a row
   changed, appends the next timeline entry. Returns `null` if nothing changed.
4. **`settle`** is one transaction: CAS to `settled`, write amounts, destination and
   `settlement_event`, append the timeline entry. A unique violation on the transfer index
   returns `"transfer_claimed"` and changes nothing; a lost CAS returns `"stale"`.
5. **`markCredited`** CAS `settled → credited` plus a timeline entry; `false` if already
   credited.
6. **`recordDeliveryFailure`** increments `delivery_attempts`, stores the error, appends
   a `delivery_failed` entry; the status stays `settled`.
7. Amounts go in and come out as `bigint`; never through `Number`.

## Acceptance tests

1. The migration applies cleanly to an empty schema.
2. `createOrder` twice with the same `externalId`: `create` called once, same row.
3. `recordPayment` twice with the same fill: one row, one timeline entry.
4. `transition` follows the table; a repeated or disallowed move returns `null` and
   changes nothing.
5. Ten concurrent `transition(waiting → processing)` calls: exactly one succeeds, one new
   timeline entry.
6. Two payments claiming the same on-chain transfer: the first `settle` returns
   `"settled"`, the second `"transfer_claimed"`.
7. `settle` then `markCredited`: timeline reads `waiting → … → settled → credited` with
   increasing `seq`; `getOrder` derives order status `paid`.
8. `recordDeliveryFailure` keeps `settled` and adds a `delivery_failed` entry.
9. An amount of `10n ** 30n` round-trips exactly.
