# M1.T3: Build owned contracts and the versioned factory manifest

Status: planned; no implementation in this change.

**Outcome:** Versioned contracts can deploy predictable addresses, execute the two payment paths and
expose independently matchable evidence.

**Learn:** CREATE2, immutable settings, ERC-3009 signatures, CCTP messages and Solidity invariants.

- Depends on: [M1.T1](M1.T1.md).
- Primary journey ownership: J1.S4, J7.S2, J12.S2.
- Policy: D28, D33, D39, D126, D134, D135, D231, X6. Invariants: I11, I12.
- Rough effort: 4–6 focused developer days, excluding external waits.
- Expected locations: contracts/src and contracts/test; generated ABI/version manifest consumed by packages/server.

Read the linked [decisions](../decisions.md), exact criteria in the
[journey spine](../journeys/settle-kit.yaml), and [technical
design](../plans/2026-10-15-deposit-sdk-technical-design.md).
Use the [checkpoint protocol](README.md#how-we-implement-together). Implement one
checkpoint per turn unless Vinay explicitly asks for a longer run.

## Checkpoint 1: Predict and deploy the same supported contract

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Implement ownerless factories and complete constructor encoding. Generate the
chain/version manifest and explain the reproducible same-address factory deployment. Verify code and
settings when an address already exists.

**Check:** Foundry checks cover predeployment, incompatible code and fixed recipients (I11). Bun
integration checks prove manifest startup rejection (J1.S4.c3–c4) and deterministic encoding (D135).

**Walk through:** Which constructor input changes the predicted address, and why does storing the
first result matter?

## Checkpoint 2: Implement manual and exact-amount execution

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Implement the D33/D231 entry points with atomic fee/payment rollback and unrelated manual
funds preserved. Freeze authorization commitments and events. Derive unique CCTP operation tags;
compose the forwarding and Settle Kit frames defined in the design.

**Check:** Foundry checks exercise limits, fee bounds, signature tampering, replay and rollback
(I11/I12). Two equal manual burns and two equal wallet burns must have distinct protected tags
(J4.S2.c18); retries of one authorization cannot execute twice.

**Walk through:** Walk from the payer's signature to the exact fields the contract recomputes before
moving USDC.

## Checkpoint 3: Implement guarded recovery and inspect the threat model

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Add zero-fee over-limit recovery and non-USDC/native-ETH rescue to the stored refund
address. Advance USDC drain sequence only for USDC drains. Handle failed transfers and reentrancy;
write focused threat-model notes.

**Check:** Prove successful and rejected recoveries under J7.S2 and rescues under J12.S2. Include a
malicious token, failed recipient transfer, rollback of the drain sequence and attempts to redirect
funds.

**Walk through:** Why does a rescue receipt prove funds reached the host but not that the payer was
repaid?

**Out of scope:** Audited-contract claims, rescue submission UI and SDK-submitted recovery
transactions.

## Done and handoff

Foundry and ABI/manifest checks pass with reproducible deployment instructions. Contracts remain
unaudited; composed-hook compatibility and the real cross-chain route remain M2.T5 gates.

**Keep as evidence:** An annotated signature-to-burn diagram plus the contract functions Vinay can
explain without reading generated ABI.

Use exact criterion/invariant IDs in tests; see the shared protocol for naming,
merge checks and the checkpoint handoff. Do not start the next task automatically.
