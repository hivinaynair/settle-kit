## Checkpoint 1: Name the data crossing package boundaries

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Define integer base-unit codecs and public data transfer objects (DTOs). Separate
provisional observations, verified manual deposits and accepted wallet attempts; keep attempt,
settlement and delivery states distinct. Describe the fixed D140 methods without implementing fake
successful methods.

Include D112/D115 history-loading, read-error and last-retrieval distinctions in client contracts.
Preserve existing account-scoped references for D114 and the quote fields used by D113. Retrieval
freshness is metadata, not a new settlement or verification state.

**Check:** Use table-driven D22 tests for amount boundaries and JSON round trips. Check invalid
amount directions against J8.S2.c4. Type-check all three packages; core must have no server, key or
RPC imports.

Walk through an empty successful history versus an unavailable read. Runtime transport/controller
checks for J8.S1.c11 and J9.S1.c4–c8 belong to M2.T4/M3.T2; this task only establishes their
contract.

**Walk through:** Given a signed payment with no chain transfer, which record exists, and why is it
not a credited deposit?

## Checkpoint 2: Validate configuration and account authority

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Define separate simulated/live configuration shapes. Validate destinations, the 32-byte
namespace, finite quote deadlines and every D128 budget. Specify the authenticated principal passed
into handlers and the ownership check used for stored payment IDs.

**Check:** Exercise J1.S1.c1 and J1.S2.c3/c5–c11 with missing settings, invalid fee bounds and a
second account requesting another account's ID. Assertions must test the stated rule, not merely the
type definition.

**Walk through:** Which values may the browser supply, and which values must the server decide?

## Checkpoint 3: Prove simulated startup is isolated

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Construct the simulated adapter without importing or initializing live signers/RPC
clients. Use fixture destinations and local signing material. Document the internal store, evidence
and submitter interfaces needed by later tasks; keep them specific to this product.

**Check:** Start with live settings absent and assert J1.S2.c12–c13. Inject dependencies that fail
if live material is loaded. Generate secret-bearing failure cases for I5 and check structured errors
and responses.

**Walk through:** Show the import/construction path that prevents test mode from reaching a real
wallet.

**Out of scope:** Database implementation, real transactions and final React components.

## Solana scope handoff (2026-10-18)

Define D143 discriminated chain/cluster, address instruction, signing-message and event-identity
shapes in checkpoint 1. Solana keys are base58 public keys; do not coerce them into EVM hex or chain
numbers. Distinguish the owner receive address from its ATA and pending setup from ready instructions.
Checkpoint 2 validates J1.S2.c14 and the D117/D128 SOL/priority-fee/rent controls; M1.T5 executes
J1.S4a deployment checks. Simulated adapters include all three sources without live keys/signatures.
Use J13.S1.c3/c6 and J14.S1.c4 to review the shape; full behavior closes in M2.T8/M2.T10.
