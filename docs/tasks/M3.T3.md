# M3.T3: Ship the Deposit interface and reference wiring

Status: planned; no implementation in this change.

**Outcome:** A developer can use the prebuilt Deposit flow in the reference app and inspect progress
without misleading money states.

**Learn:** Product interaction, accessible payment states, safe address instructions and
CSS-variable theming.

- Depends on: [M3.T2](M3.T2.md), [M2.T2](M2.T2.md).
- Primary journey ownership: J1.S5, J2.S1, J2.S2, J2.S6, J3.S1, J3.S2, J3.S6.
- Policy: D13, D18, D28, D39, D42–D44, D124, D131, D140. Invariants: I11, I12.
- Rough effort: 2–3 focused developer days, excluding external waits.
- Expected locations: packages/react/src/Deposit and styles; apps/demo integration.

Read the linked [decisions](../decisions.md), exact criteria in the
[journey spine](../journeys/settle-kit.yaml), and [technical
design](../plans/2026-10-15-deposit-sdk-technical-design.md).
Use the [checkpoint protocol](README.md#how-we-implement-together). Implement one

## Checkpoint 1: Build both payment entry paths

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Render the receive-first wallet quote, disclosed fee and manual address alternative using
the shared hooks. Show route-specific limits and manual estimates. Keep the simulated widget and QR
visibly labeled.

**Check:** Check J1.S5.c1–c3, J2.S1.c4/c9–c10 and J3.S1.c4/c8/c10–c11. The early preview must
identify all simulated progress as simulated.

**Walk through:** Why does changing to the address option change the promise from exact credit to
estimated credit?

## Checkpoint 2: Keep address text, copy and QR synchronized

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Use the account/chain-scoped stored record for all instructions. Clear stale state during
selection changes; ignore incoming lookalikes and delayed responses. Provide full address/chain
inspection and accessible status announcements.

**Check:** Compare displayed address, clipboard and decoded QR on both chains; switch mid-load and
feed poisoning activity (J2.S1.c11–c13, J3.S1.c12–c14, J9.S2.c4–c5). Theme without monorepo UI
dependencies.

**Walk through:** How would you demonstrate that the QR cannot still point at the previous account
during loading?

## Checkpoint 3: Wire the reference app and explain progress

- [ ] Reviewed with Vinay; focused checks and remaining evidence recorded.

**Build:** Mount authenticated handlers and one background engine. Render awaiting-minimum,
provisional/reorg, processing, attention and account-update-pending states. Add the small
operator-authorized alert/timeline view as its backend becomes available.

**Check:** Verify continued targeted scans after deposits/top-ups and host acknowledgment gating
(J2.S2.c2/c5, J2.S6.c2–c3, J3.S6.c2–c3). Preview with controlled evidence; rerun actual host
integration in M4.T1.

**Walk through:** Point to the exact evidence behind each displayed step from Received to account
credited.

**Out of scope:** Checkout screens, docs-site work and a broad component suite.

## Done and handoff

The usable simulated preview and reference wiring pass browser checks. Live completion must not be
inferred from simulated progress or placeholder alerts.

**Keep as evidence:** A short product walkthrough plus screenshots labeled with the evidence behind
their displayed states.

Use exact criterion/invariant IDs in tests; see the shared protocol for naming,
merge checks and the checkpoint handoff. Do not start the next task automatically.
